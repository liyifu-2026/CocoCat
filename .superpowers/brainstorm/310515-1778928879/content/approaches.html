三种激活方案对比

需求：CocoCat 内专属 kb-agent，事件驱动 + 定时巡检，双向服务（后台维护 + 交互查询）

A

最小改动：扩展现有 Worker + 加 KB 工具

在现有 TaskWorker 里注册 kb-agent agent 类型。Worker 认领 kb 任务后分发给 kb-agent 执行 ReAct 循环。KB 工具（search_kb、write_wiki、dedup、lint 等）直接加到 agent 工具集。Cron 定时生成本维护任务写入 tasks 表。

B

专用 KBAgent：独立运行循环

新建 KBAgent 类，拥有自己的生命周期和调度循环。不依赖 TaskWorker，有自己的工具集、自己的 cron 调度器、自己的 WebSocket 通道。用户可通过对话界面直接和 kb-agent 交互，类似于一个独立的「知识管理员」。

C

推荐：KB 服务层 + 薄 agent 封装

把现有散落在多个文件里的 KB 能力（dedup、lint、overview、graph、cascade）抽成一个 KBService 统一服务层。Agent 工具是 KBService 的薄封装。Worker 继续分发 kb 任务给 kb-agent。Cron 通过生成任务触发巡检。可测试、可复用、改动适中。

方案 C 的优势（推荐）

  • KBService 可以独立测试，不依赖 LLM
  • Agent 工具只是薄封装，不重复造轮子
  • 复用现有 TaskWorker + tasks 表，不改核心架构
  • 以后换 agent 框架或调度策略不需要改 KB 逻辑
  • 改动量适中，约 800-1200 行新代码

方案 A 的劣势

  • KB 逻辑散落在 agent 工具里，难以测试
  • Worker 与 KB 耦合深，后期不好拆

方案 B 的劣势

  • 独立运行循环 = 重复实现 agent 基础设施
  • 改动量大（~2000+ 行），与现有架构偏离
